Vol. 18 | October 4, 2026


THE FIRST AGENTIC RANSOMWARE


On September 25, 2026, Microsoft disclosed Storm-3168, tracked elsewhere as JADEPUFFER, in what multiple independent researchers describe as the first documented agentic ransomware operation. [1] [2] The distinction matters precisely. This was not a human operator running scripted tooling. An AI agent, operating under the attacker's direction, drove the intrusion directly: roughly 15 hours and 30 minutes of autonomous enumeration across a victim's Azure environment, followed by more than 150 destructive and credential collection operations attempted in about 35 minutes, including the deletion of more than 100 storage accounts in a seven minute window. [2] No human incident response process is built to react inside seven minutes. That gap is the entire story.

The intrusion's origin was almost disappointingly ordinary. The compromised Azure service principal credentials, a client ID, client secret, and tenant ID, had been inadvertently exposed in a public GitHub issue. [1] An agent did not need a novel exploit to cause unprecedented damage. It needed standing credentials and the speed to act on them before anyone could intervene.

The same month, Microsoft shipped two capabilities aimed at a related but distinct problem: visibility into the agents an organization is actually running. Agent 365 introduced an Agent Registry that surfaces unmanaged local agents discovered through Microsoft Defender, Entra, and Intune, covering more than twenty agent types including coding agents, AI desktop applications, and both local and remote Model Context Protocol servers. [4] Alongside it, Microsoft extended Zero Trust network controls to agent traffic itself, covering Copilot Studio agents and local agents, including named examples like OpenClaw, running on user endpoints. [5] Storm-3168 and this governance expansion did not cause each other. But they describe the same emerging reality from opposite sides: agents are now fast and capable enough to cause Storm-3168 level damage, and organizations are only beginning to build the visibility needed to know which agents they are even running.


JADEPUFFER: WHEN RANSOMWARE BECOMES AGENTIC


The technical sequence behind Storm-3168 is worth walking through because the targeting choices reveal deliberate strategy, not random destruction. After the extended enumeration phase mapped the victim's Azure tenant, the agent executed its destructive phase against Storage Accounts, SQL databases, Key Vaults, Function Apps, Virtual Machines, App Services, and recovery protection locks specifically. [2] Targeting recovery protection controls alongside the primary resources is the agentic equivalent of classic ransomware logic: disable the ability to restore before destroying what would need restoring. The difference is that a human operator working through that same sequence manually would need hours. This agent needed seven minutes for the storage account deletion phase alone.

Roughly 30 minutes after the final destructive action, the same compromised service principal issued more than 30 successful ListKeys requests, including against storage accounts tied to Azure Site Recovery. [2] Retrieving those keys would have given the operator a path to access or exfiltrate backup and recovery data specifically, suggesting the campaign's objective extended beyond destruction into positioning for further access or a parallel extortion angle. Organizations examining Microsoft's writeup noted that the resources which survived the sweep were specifically those protected by resource locks configured before the intrusion began. [3] Locks applied during or after an active destructive sequence of this speed are not a realistic defense. Locks applied in advance, as a standing configuration, were the only control that functioned at the speed this attack operated at.

The lesson here is not really about AI agents as a novel threat category in the abstract. It is about what changes when a threat that has existed for years, ransomware driven by a compromised cloud identity, gets executed by something that does not pause, does not need to context switch, and does not tire across a 150 operation sequence. Detection and response architectures built around a human-paced attacker assumption are not simply slower against an agentic adversary. They may not functionally exist as a defense at all within the actual window the attack runs in.


AGENT 365 AGENT REGISTRY: FINDING THE AGENTS YOU DIDN'T KNOW ABOUT


Microsoft's September additions to Agent 365 address a different, earlier stage of this same problem. The Agent Registry's purpose is discovering local agents that were never centrally registered anywhere, the same governance gap this series tracked in Vol. 13 with Defender's agent posture risk preview and in Vol. 14 with multi-tenant Agent 365 management. [4] Coverage now spans more than twenty agent types, explicitly including coding agents and both local and remote MCP servers, surfaced through signals from Defender, Entra, and Intune rather than requiring an agent to have been deliberately onboarded to be visible. [4]

The Zero Trust extension to agent traffic is the complementary piece, applying Entra's network control model to the traffic agents generate, whether that traffic originates from a Copilot Studio agent or a local agent running directly on an endpoint. [5] Naming specific local agents like OpenClaw in the announcement signals that Microsoft is treating the local, unregistered agent population as a known, cataloged risk surface rather than a hypothetical one.

It is important to be precise about what this governance expansion does and does not address relative to Storm-3168. The Agent Registry and Zero Trust extension are built to answer the question of which agents an organization is running and what their network traffic looks like. Storm-3168's root cause was an exposed service principal secret, a credential hygiene failure that predates and sits entirely outside the agent governance problem these tools solve. An organization could deploy every capability described here and still be exactly as exposed to a Storm-3168 style attack if its secrets management practices remain unchanged. The two tracks are both necessary, and neither substitutes for the other.


THREE ITEMS REQUIRING IMMEDIATE ATTENTION


1. Audit public and internal code repositories, including issues, commit history, and logs, for exposed service principal credentials or other standing secrets immediately. Storm-3168's entire campaign originated from a client secret left in a public GitHub issue, a basic hygiene failure that enabled agent speed destruction once in attacker hands. [1]

2. Apply Azure resource locks and recovery protection configurations proactively, before an incident, not as a response to one. Microsoft's own analysis found pre-configured locks were the resources that survived Storm-3168's deletion sweep; anything unprotected in advance was gone within minutes. [2] [3]

3. Deploy Agent 365's Agent Registry to discover unmanaged local AI agents across your endpoint fleet, and apply Entra Zero Trust network controls to agent traffic once that inventory exists. Treat this as the discovery exercise this series has recommended since Vol. 13, not an assumption that existing governance already covers agents running locally. [4] [5]


THE ROAD AHEAD


Storm-3168 should recalibrate how security leaders think about detection and response timelines generally, not only for cloud identity compromise specifically. A defense architecture built around a mean time to detect and a mean time to respond measured in hours, the standard most SOCs still plan around, has no meaningful answer to an attack that completes its destructive phase in seven minutes. The practical implication is that prevention, credential hygiene, standing resource protections, and least privilege scoping, carries more of the actual defensive weight than detection and response can carry once an agentic attacker is already acting inside an environment.

Agent 365's Agent Registry and the Zero Trust extension to agent traffic are Microsoft building toward visibility into the growing population of agents operating inside organizations, which is real and necessary progress. But Storm-3168 is a reminder that the oldest, least glamorous failure mode, a secret exposed somewhere it should never have been, is still sufficient on its own to hand an attacker everything an agent needs to cause this level of damage. Agent governance tooling and basic secrets hygiene are not competing priorities. Both are now prerequisites, and neither one covers for the other.


FOR DISCUSSION

1. Storm-3168 completed its most destructive phase, deleting more than 100 Azure storage accounts, in approximately seven minutes. Does your incident response plan assume a detection and containment window measured in hours, and if so, what would actually happen to your environment if an agentic attacker operated at this speed?

2. The resources that survived Storm-3168's sweep were specifically those protected by resource locks configured before the intrusion began. Does your organization apply standing protective configurations proactively across critical cloud resources, or are locks and protections typically applied reactively during an incident?

3. Agent 365's new Agent Registry discovers local AI agents that were never centrally registered. Does your organization have a current, complete inventory of coding agents, AI desktop applications, and MCP servers running on endpoints, or would a discovery scan likely surface agents nobody on the security team knew existed?
