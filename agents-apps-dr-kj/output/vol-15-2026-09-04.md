AGENTS & APPS WITH DR. KJ
Vol. 15 | September 4, 2026


AGENTS ARE APPS NOW


This series has spent fourteen issues covering how AI accelerates attackers and defenders. This issue turns to a question underneath all of that: what happens when the agents themselves are the vulnerable software. Microsoft's August 2026 security updates disclosed two critical elevation of privilege flaws, not in Windows, not in SharePoint, but directly inside two of Microsoft's own AI agent products. CVE-2026-62830 affects Azure SRE Agent, the AI system that autonomously monitors, diagnoses, and remediates issues across Azure infrastructure, and carries a CVSS score of 9.9. [1] CVE-2026-59118 affects Copilot Cowork and carries a CVSS score of 9.3. [3] Both are, at their core, ordinary authorization bugs, the same bug class that has always existed in conventional applications.

What is not ordinary is the blast radius. A traditional application's authorization bug typically exposes what that application itself can touch. An autonomous agent's authorization bug exposes everything the agent was empowered to autonomously act on, because that scope is the entire point of building the agent in the first place. Azure SRE Agent exists specifically to reach broadly across an environment and take action without waiting for a human. CVE-2026-62830 turned that design goal into the vulnerability's actual impact.

Microsoft's own research organization published a partial answer to the trust question these flaws raise. On August 19, 2026, Microsoft open sourced ThinkingBox, a sandbox and benchmark built to test whether AI agents can reliably complete real business tasks, not just succeed once. [4] Its headline finding is sobering on its own: across every model tested, the strongest achieved a 65.36 percent single attempt success rate, but only a 25.25 percent success rate when required to complete the same task reliably across twenty repeated trials. [4] An agent that works most of the time is not the same as an agent that can be trusted with broad delegated access, and this issue's two vulnerabilities are what that gap looks like when it goes unaddressed.


WHEN THE AGENT'S OWN IDENTITY BECOMES THE BLAST RADIUS


Azure SRE Agent operates using a delegated identity model, specifically an On Behalf Of, or OBO, authentication flow, that lets it act with the permissions needed to diagnose and remediate issues across the infrastructure it manages, runbooks, telemetry systems, incident tooling, and the Azure resources those systems touch. CVE-2026-62830 is a missing authorization flaw, CWE-862, that let a low privileged remote attacker elevate privileges over the network with no user interaction required and low attack complexity. [1] [2] The vulnerability's scope changed vector means the impact was not contained to the agent's own boundary. An attacker who exploited it inherited the agent's service principal permissions across the entire environment the agent's managed identity could reach. [1]

This is the structural risk unique to autonomous operations agents, distinct from the risk profile of a conventional application. A compromised web application typically exposes the data and functions that application was built to handle. A compromised autonomous remediation agent exposes everything that agent was trusted to fix, which by design is broad, cross cutting, and often includes exactly the incident response and telemetry infrastructure a security team would use to detect the compromise in the first place.

Microsoft addressed CVE-2026-62830 with a service side fix, meaning no customer action was required to apply a patch. Microsoft's guidance to customers instead focused on verification: audit managed identity assignments tied to any autonomous agent deployment, review the RBAC scope those identities actually hold against what the agent's function requires, and monitor for anomalous privilege elevation events. [1] The patch closed the specific flaw. It did not answer whether the identity scope granted to that agent, or any other autonomous agent an organization runs, is appropriately narrow to begin with.


COPILOT COWORK AND THE PATTERN REPEATING


CVE-2026-59118 is a separate vulnerability in a separate product, Copilot Cowork, but the underlying bug class is the same family: improper authorization, CWE-285, this time allowing an attacker to elevate privileges over the network with low attack complexity, requiring some user interaction to trigger. [3] Two unrelated agent products, developed by different teams, disclosed in the same monthly security update, sharing the same root cause category.

That repetition is the more useful signal than either vulnerability individually. One authorization flaw in one agent product is a bug. Two critical authorization flaws in two separate agent products in the same update cycle is a pattern worth treating as a portfolio level question rather than two isolated patches. Security teams evaluating any Microsoft Copilot or agent product, not only the two named here, should specifically confirm current patch levels and review whether their deployment includes any user facing flows where an authorization check could be the single point of failure standing between routine use and full privilege escalation.


TESTING WHETHER AGENTS CAN BE TRUSTED WITH THE WORK


ThinkingBox is worth understanding on its own terms, not only as context for this issue's two vulnerabilities. The framework evaluates agents against 507 policy conditioned workflows spanning retail, hospitality, auto insurance, internal IT support, and consulting scenarios, and it grades success by checking what the agent actually changed in the underlying system state, not by trusting the agent's own account of what it did. [4] [5] That design choice matters directly for security evaluation: an agent's self report of successful, policy compliant behavior is not evidence of it, and a testing framework that only checks stated outcomes would miss exactly the kind of silent scope violation an authorization bug like CVE-2026-62830 represents.

The reliability gap ThinkingBox surfaces, a 65 percent single attempt success rate collapsing to 25 percent reliability across repeated trials for the strongest model tested, is a useful benchmark for any organization deciding how much autonomous authority to grant an agent. [4] An agent that reliably succeeds a quarter of the time it is asked to complete a stateful, multi step business task is not yet an agent that should hold broad, standing delegated access of the kind Azure SRE Agent was built with. Microsoft releasing this framework as open source, rather than keeping the evaluation methodology proprietary, suggests the company wants this kind of reliability testing treated as a baseline industry practice rather than a competitive differentiator.


THREE ITEMS REQUIRING IMMEDIATE ATTENTION


1. Audit managed identity and RBAC scope for every autonomous agent deployment, not only Azure SRE Agent. Following Microsoft's CVE-2026-62830 guidance, confirm the permissions granted to each agent's identity match what its function actually requires, and set up monitoring for anomalous privilege elevation events tied to agent service principals. [1]

2. Confirm Copilot Cowork is current on the August 2026 security update addressing CVE-2026-59118, and review any user facing flows in your Copilot and agent deployments for authorization checks that represent a single point of failure. [3]

3. Evaluate agent reliability with a structured framework, such as ThinkingBox, before expanding an agent's delegated access. Treat a low pass rate across repeated trials as a direct input to how much autonomous authority that agent should be granted, not a separate quality metric from the security decision. [4]


THE ROAD AHEAD


This issue is a deliberate change of focus from the pattern this series has tracked since Vol. 8, AI accelerating discovery and remediation of vulnerabilities elsewhere in the environment, to the vulnerabilities showing up inside the agents themselves. The finding is not encouraging on its own: two critical authorization bugs in two separate Microsoft agent products in a single update cycle, and independent research showing the strongest available models complete complex business tasks reliably only about a quarter of the time.

But the response this issue documents is proportionate to the finding. Microsoft's service side fix and audit guidance for CVE-2026-62830, and the open release of ThinkingBox as a reliability benchmark, both treat agent authorization and agent reliability as first class security questions rather than an extension of conventional application security review. The organizations that will manage this transition well are the ones applying the same operational discipline to agent identity scope and reliability testing that they already apply to conventional application security, before granting the next agent broad standing access rather than after.


FOR DISCUSSION

1. CVE-2026-62830's blast radius extended across everything Azure SRE Agent's managed identity could reach, not just the agent itself. Does your organization's security review process for autonomous agents evaluate the full scope of what the agent's identity can touch, or does it stop at reviewing the agent's own interface and stated function?

2. Two critical authorization vulnerabilities appeared in two separate Microsoft agent products in the same update cycle. Does your patch management process treat AI agent and Copilot products with the same priority and audit cadence as core infrastructure, or are they still being tracked separately?

3. ThinkingBox found that the strongest AI model tested reliably completed stateful business tasks only 25 percent of the time across repeated trials, despite a 65 percent single attempt success rate. How does your organization currently decide how much autonomous, delegated access to grant a new agent, and does that decision account for reliability data like this?
