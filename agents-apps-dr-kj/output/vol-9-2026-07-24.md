PATCHED BUT NOT CLEAN


CISA issued an alert on July 14, 2026 that changed the framing of the SharePoint story this series has been following for two issues. The alert was not another patch reminder. It was a warning that patching four separate vulnerabilities, added to the Known Exploited Vulnerabilities catalog on April 14, July 1, July 14, and July 16, does not by itself remove the attackers who already used them. [1] Threat actors chaining these flaws have been stealing Internet Information Services machine keys during the intrusion, and those keys let an attacker forge trusted authentication material on the server independent of whatever patch level the system reaches afterward. A patched server can still be a compromised server.

The fourth vulnerability in that chain, CVE-2026-58644, a critical deserialization flaw enabling unauthenticated remote code execution, carried a federal remediation deadline of July 19, 2026. [2] That deadline has passed. Any organization running on-premises SharePoint Server that has not both patched and hunted for persistence artifacts is now operating past the government's own floor for acceptable exposure.

A second thread this cycle involves identity rather than infrastructure. Renewed reporting in mid-July on Kali365, a phishing-as-a-service platform the FBI's Internet Crime Complaint Center first flagged in May, put a number on the damage: Florida residents alone reported more than 12 million dollars in phishing losses, with Kali365 identified as an active contributor. [3] [4] The platform hijacks Microsoft 365 sessions by abusing a legitimate OAuth authentication flow, without ever touching a password.

Different attack surfaces, same underlying lesson. A control that stops the initial exploitation, a patch, a password policy, is necessary and insufficient on its own. Both stories this issue are about what has to happen after the control is in place.


FOUR VULNERABILITIES, ONE PERSISTENCE MECHANISM


The SharePoint chain CISA described spans three months of disclosures: CVE-2026-32201, added to KEV April 14, CVE-2026-45659, covered in Vol. 7 after its July 1 KEV addition, CVE-2026-56164, added July 14, and CVE-2026-58644, added July 16. [1] [2] Attackers have used combinations of these flaws to bypass authentication, achieve remote code execution, and then conduct post-exploitation activity focused on one specific objective: stealing the IIS machine keys that SharePoint and ASP.NET use to validate authentication tokens and application state.

That objective is what makes this different from a standard exploit-and-patch cycle. A machine key is not a credential in the conventional sense. It is cryptographic material the server itself trusts to validate that a token or session is legitimate. An attacker who has exfiltrated a server's machine keys can forge trusted material against that server even after every known vulnerability is patched, because the patch closes the entry point without invalidating material the attacker already holds.

CISA's guidance reflects that distinction directly. The recommended sequence is to hunt for and remediate intrusion artifacts, including machine key harvesting tools, before rotating the machine keys. [1] Rotating first and hunting second leaves the harvesting mechanism in place to simply capture the new keys. Sequence matters here in a way it does not for most patch and reboot cycles.

Additional hardening CISA outlined includes establishing tailored logging to catch anomalous activity that patch compliance alone will not surface, avoiding direct internet exposure of SharePoint servers where that exposure is not operationally necessary, and reviewing Microsoft's official SharePoint Server hardening guidance rather than treating the monthly patch as complete remediation. [1] For any organization that patched CVE-2026-45659, CVE-2026-56164, or CVE-2026-58644 without a corresponding compromise assessment, the patch addressed the vulnerability. It did not necessarily address the intrusion.


KALI365 AND THE DEVICE CODE BLIND SPOT


Kali365 targets a different assumption: that multi-factor authentication, once enabled, closes the identity attack surface. It does not close all of it.

The platform abuses the OAuth 2.0 device authorization grant, a flow built for devices with limited input capability, a smart TV or a conference room system, to authenticate through a second device using a short code. [4] Kali365's phishing lures direct a target to the real Microsoft device code entry page and instruct them to enter a code the attacker generated. The victim is authenticating on a legitimate Microsoft page. What they are authorizing is the attacker's device, not their own. No password is intercepted, and no fake login page is involved, which is precisely why this technique evades awareness training built around spotting spoofed login pages. [4]

Kali365 also offers a second mode, described as an adversary-in-the-middle proxy that captures session cookies and tokens directly as the victim authenticates through attacker-controlled infrastructure. [4] Between the two modes, the platform covers both the device code abuse path and the more familiar token-theft path in a single subscription product, reportedly priced as low as 250 dollars a month. [4] The FBI's renewed warning in mid-July, with Florida's reported losses used as the concrete illustration, indicates this is an active and ongoing campaign rather than a contained incident from its April emergence. [3]

The defensive gap is specific and addressable. Organizations that have not restricted the OAuth device code flow through Conditional Access, or that are not monitoring sign-in logs for device code grant types outside expected use cases such as shared conference room hardware, have a live blind spot regardless of how strong their password and standard MFA policies are. This is the same operating pattern this series flagged with SearchLeak in Vol. 5: the attack does not defeat the control, it operates through a legitimate mechanism the control was not built to restrict.


THREE ITEMS REQUIRING IMMEDIATE ATTENTION


1. Sequence SharePoint remediation correctly: hunt, then rotate. Any environment that has patched CVE-2026-45659, CVE-2026-56164, or CVE-2026-58644 should now conduct a compromise assessment for machine key harvesting artifacts before rotating IIS machine keys, following CISA's guidance directly. [1] Rotating keys first without removing the harvesting mechanism accomplishes nothing.

2. Restrict OAuth device code authentication through Conditional Access. Organizations should identify whether the device code flow is enabled tenant-wide and, where it is not required for legitimate limited-input device scenarios, restrict it. Sign-in logs should be reviewed for device code grant activity that does not match known conference room or shared device use. [4]

3. Treat the SharePoint hardening guidance and the Kali365 advisory as compromise-assumption exercises, not patch checklists. Both cases this issue describe attacker techniques that survive the standard remediation step. Security teams should ask, for each control deployed this year, what evidence would show the control was bypassed rather than simply confirming the control is present.


THE ROAD AHEAD


This series has tracked an escalating pattern in SharePoint's exposure across three issues. Vol. 7 covered a single vulnerability that Microsoft initially rated unlikely to be exploited. Vol. 8 covered the record patch volume driven by Microsoft's AI-assisted vulnerability discovery, with SharePoint among the products carrying zero-days at disclosure. This issue covers CISA's acknowledgment that the same product has now been targeted through a chain of four vulnerabilities over three months, with attackers specifically pursuing persistence material that outlives the patch. The pattern is not that SharePoint has an unusual number of bugs. It is that a high-value, often internet-facing product accumulates sustained attacker attention once it is established as a productive target, and that attention does not stop when one vulnerability in the chain gets fixed.

Microsoft's July progress report on its Secure Future Initiative describes continued investment in AI-powered defense and in strengthening security foundations against exactly this kind of sustained, multi-stage attacker pressure. [5] The report is a statement of direction rather than a specific control security teams can deploy this quarter, but it is a useful marker of where platform investment is heading: toward detecting the behavior that follows initial compromise, not only the vulnerability that enabled it.

The throughline across recent issues holds. Patch compliance is necessary. It is not the same as confirming an environment is clean. Organizations that measure their security posture by patch cadence alone are answering a different question than the one CISA and the FBI are both raising this cycle.


FOR DISCUSSION

1. CISA's guidance for the SharePoint machine key compromise specifies hunting for persistence artifacts before rotating keys, not after. Does your incident response process have a defined compromise assessment step for infrastructure vulnerabilities, or does your process end at patch deployment?

2. Kali365 hijacks Microsoft 365 sessions through a legitimate OAuth flow that standard password and MFA controls do not restrict. Has your organization reviewed whether the device code authentication flow is enabled beyond its legitimate use cases, and are your sign-in logs monitored for that grant type specifically?

3. Three consecutive issues of this series have covered new SharePoint exploitation activity. If your organization runs on-premises SharePoint Server, does your security team treat it as a standing high-attention asset with continuous monitoring, or does it receive attention only when a new CVE is disclosed?
